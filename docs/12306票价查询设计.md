## 一、调研结论（网上公开资料 + 实测验证）

12306 没有官方开放 API，但网页端 `kyfw.12306.cn` 的查询接口是公开的 JSON 接口，
无需登录即可查车次与票价。开源社区已有多个成熟封装（如
[mcp-server-12306](https://github.com/drfccv/mcp-server-12306)、
[train-ticket-mcp](https://pypi.org/project/train-ticket-mcp/)），
本设计参考其接口用法并对我们的"取最高二等座价"场景做了裁剪和修正。

### 用到的 3 个接口（全部 GET，无需登录）

| # | 端点 | 用途 |
|---|------|------|
| 1 | `https://kyfw.12306.cn/otn/leftTicket/init` | **会话初始化**：每次会话先访问一次取 cookie（JSESSIONID 等），否则查询接口易被反爬拦截 |
| 2 | `https://kyfw.12306.cn/otn/leftTicketPrice/queryAllPublicPrice` | **票价查询（核心）**：一次请求返回当日全部车次的所有席别价格，无需逐车次二次查询 |
| 3 | `https://kyfw.12306.cn/otn/resources/js/framework/station_name.js` | **车站名→三字码表**（全国 3000+ 车站），本地缓存为 `station_codes.json` |

### 票价接口详情

```
GET /otn/leftTicketPrice/queryAllPublicPrice
    ?leftTicketDTO.train_date=2026-10-24      # 出发日期
    &leftTicketDTO.from_station=BJP           # 出发站三字码
    &leftTicketDTO.to_station=SHH             # 到达站三字码
    &purpose_codes=ADULT                      # 成人票
```

- 返回 `data[]`，每项 `queryLeftNewDTO` 内含车次、发到站、历时 `lishi`，
  以及各席别价格字段：`ze_price`(二等座)、`zy_price`(一等座)、`swz_price`(商务座) 等；
- **价格单位为"角"**：`"8200"` = 820.0 元（末位是小数位），`"--"` 表示该席别不存在；
- 必要请求头：`User-Agent`（浏览器 UA）、`Referer: .../leftTicket/init`、`X-Requested-With: XMLHttpRequest`；
- 12306 证书链在部分环境校验失败，需 `verify=False`（仅读公开数据，可接受）。

### 实测踩到的三个坑（已在 fare_query.py 中处理）

1. **城市聚合**：查"北京(BJP)→上海(SHH)"会返回同城全部车站的车次——
   对"城市到城市"预算是好事；但"同城"边界用站名前缀判断有例外：
   清河/福田/武昌/汉口是市区大站却不以城市名开头（前缀法会误排除），
   盛泽/太仓等远郊县市站又会被误纳入或误排除。
   → 对策：**直接用 station_name.js 官方的"所属城市"字段判定同城**
   （官方权威归属表，如 盛泽属苏州、福田属深圳、汉口属武汉），
   缓存于 `station_codes.json`；归属缺失时回退站名前缀匹配。
2. **绕路车**：即便同城，个别环线车次走超长径路、历时数十倍于直达车（实测 盛泽→无锡
   绕行 406 分钟 570 元，而苏州市区→无锡市区直达 10 分钟 29 元）。
   → 对策：**剔除历时 > max(2×最短历时, 最短历时+60分钟) 的车次**再取最高价。
3. **预售期约 15 天**：预算编制往往在出行前数月，查不到未来日期。
   → 对策：超出预售期自动回退到最近可售日。票价按车次定价、与日期基本无关
   （浮动票价线路以查询日为准，记录 query_date 留痕）。

### 为什么不用老接口 `leftTicket/query + queryTicketPrice` 两步法

网上早期教程（如 [wp.mis2erp.com 的实例](http://wp.mis2erp.com/archives/880.html)）是
先查余票串再逐车次调 `queryTicketPrice` 取价，每个车次一次请求、字段按 `|` 下标解析，脆且慢。
`queryAllPublicPrice` 一次返回全部车次价格，是我们场景的最优端点。

## 二、fare_query.py 设计

### 标准使用流程

```bash
# 每期做预算前：一条命令完成"刷新票价 + 重建预算表"
python3 rebuild_budget.py 院系申报表.xlsx -o 预算表.xlsx --refresh
```

`--refresh` 会先对本表涉及的全部分段按窗口联网重查最新最高价（覆盖 fares.json 缓存并留痕），
再重建预算表。窗口自动选择：**表内拟参访日期（E列）落在 12306 预售期（约15天）内时，
按拟定窗口查**（如 E=10.25-10.29 → 窗口 5 天）；否则默认"明天起 14 天"预售期全量窗口，
可用 `--refresh-days N` 调整。三档联网强度按需选择：

| 模式 | 行为 | 适用 |
|------|------|------|
| （默认） | 纯读 fares.json 缓存，零网络 | 日常试算、重复重建 |
| `--online` | 仅缺失分段联网补齐 | 新增了实践地 |
| `--refresh` | 涉及分段全部重查最新价 | **每期正式预算前** |

### fare_query.py 独立用法

```bash
# 1. 单日查询（默认查明天）
python3 fare_query.py 北京 上海 [--date 2026-10-24] [--json]

# 1b. 窗口查询：从起始日起逐日查 N 天取最高（超预售期的日子自动跳过）
python3 fare_query.py 北京 上海 --days 14                     # 预售期全量窗口
python3 fare_query.py 北京 合肥 --date 2026-10-25 --days 5    # 指定拟定窗口

# 2. 校验：fares.json 缓存价 vs 实时价（只读，标出过时项；可加 --days 用窗口口径）
python3 fare_query.py --check fares.json [--days 14]

# 3. 刷新：用实时最高价重写 fares.json 全部 segments，并写 meta 留痕
python3 fare_query.py --update fares.json [--days 14]

# 4. 补段：查询新分段并追加进 fares.json
python3 fare_query.py --add 北京-合肥 合肥-上海 [--days 14]
# 人工录入（无直达车的段，打 manual 标记；预算 --refresh 时自动重试联网，仍无直达则提示"待人工复核"）
python3 fare_query.py --set 北京-林芝=1275 --note "北京-拉萨1146+拉萨-林芝129"
```

### 取数口径（与主设计 §3.3 对齐）

- **窗口查询**：支持指定窗口 `--date 起始日 --days N` 逐日查询、取窗口内最高价。
  12306 预售期约 15 天，窗口中超出预售期的日子自动跳过（`days_skipped` 留痕）；
  浮动票价按星期几波动，**窗口 ≥7 天可覆盖全周口径，默认建议 14 天（预售期全量）**；
  若拟定出行窗口落在预售期内（如学期中实践），直接按该窗口查；
- 每段取窗口内**有二等座车次中的最高价**（G/D/C 均有二等座；普速无二等座自动不参与）；
- 结果留痕：最高价、达成车次、发到站、**最高日**、查询窗口、查询天数写入 fares.json 的 `meta`；
- 限速 1 秒/请求 + 失败重试 3 次 + 会话被踢自动重建，避免触发反爬；
- 车站码本地缓存 `station_codes.json`，首次运行自动拉取。

### 与 rebuild_budget.py 的衔接（缓存优先、联网兜底）

```
rebuild_budget.py --online ：
  B列实践地 → 行程链(北京→A→B→北京) → 逐段查 fares.json
      ├── 命中 → 直接用缓存价（零网络）
      └── 缺失 → fare_query.FareClient().max_fare() 联网查 → 写回 fares.json → 本行即刻可用
```

即主设计 §3.3 的"**B 为主、A 校验**"混合模式落地：
 fares.json 仍是预算表的稳定数据源（可复核、可手工改），
 `--online` 负责消除"待查"，`--check/--update` 负责定期校正缓存价。

### 实测结果（2026-10-22 查询 10-23/24 车次）

| 分段 | 实时最高价 | 达成车次 | fares.json 缓存 |
|------|-----------:|----------|----------------:|
| 北京→上海 | 820.0 | G633/G751 | 672.0 ⚠过时 |
| 北京→南京 | 644.0 | G5 | 532.0 ⚠过时 |
| 北京→成都 | 934.0 | G1591等 | 883.0 ⚠过时 |
| 深圳→珠海 | 144.5 | G1024等 | 144.5 ✓ |
| 北京→深圳 | 1107.5 | G305等 | 1107.5 ✓ |
| 苏州→无锡 | 29.0 | G7030等 | 23.0 |
| 合肥→上海 | 285.0 | G3244/G3248 | （缺，原总价含 200 口径） |

> 2026 年高铁浮动票价普遍上调，种子库（源自 2026 暑假预算表）多数偏低——
> 这正是需要自动查询的原因。建议每期预算编制前跑一次 `--update`。

## 三、已知边界与人工兜底

### 附：城市聚合体检结果（2026-10-22，20 个查询全覆盖，v2 官方城市归属口径）

对 fares.json 全部 12 个分段 + 广州/杭州/武汉/西安往返逐一核查 12306 返回的全部车次：

- **同城判定改用官方"所属城市"字段**（station_name.js 第 8 位），修正了站名前缀法的两类错误：
  - 误排除（市区大站不带城市名）：清河（北京）、福田（深圳）、武昌/汉口（武汉）——现已正确纳入，
    北京-深圳 1107.5→1115（福田 G1025）；
  - 误纳入/误排除的远郊县市站（盛泽/太仓/常熟/张家港属苏州，江阴/惠山属无锡）——
    现按官方归属纳入同城池，但其中**绕路车全部被历时过滤排除**
    （盛泽→无锡 570 元/406min、苏州南→无锡 307 元/217min 等 14 趟）；
- **口径影响**：行政同城远郊站纳入后个别分段略微上浮——北京-苏州 777→794
  （北京南→太仓，太仓属苏州）、苏州-无锡 29→61（太仓→江阴）。方向保守（只可能高估），
  决算以实际车票为准不会超支；如某支队行程明确为市区间，可在 fares.json 手工改低；
- **动卧/普速夜车**（D17 北京→上海 741min 等）由历时过滤一并排除，不参与最高价。

### 边界与兜底

| 情况 | 行为 |
|------|------|
| 无直达车（如部分小城市） | 报"未查到二等座车次"，仍走"待查"人工兜底（主设计 §六.3 中转取法待定） |
| 远郊新站价格高于市区站 | 属正常顶格（如 北京南→苏州南 777）；支队实际购票一般更低，决算不超 |
| 反爬拦截 | 自动重试 + 会话重建；连续失败报错退出，不影响 fares.json 已有数据 |
| 机票更优线路 | 不在本工具范围，仍按主设计例外规则人工处理 |

## 四、合规说明

- 仅查询公开票价数据，不登录、不购票、不存储任何个人信息；
- 内置限速（≥1秒/请求），预算场景每期仅数十次查询，对 12306 无压力；
- 参考项目均采用相同接口（MIT 许可的 [mcp-server-12306](https://github.com/drfccv/mcp-server-12306) 等），属社区通行做法。
